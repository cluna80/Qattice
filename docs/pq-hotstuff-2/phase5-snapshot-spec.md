# Snapshot recovery specification (one recommended design; DRAFT for owner approval)

**Nothing here is implemented, activated or approved.** Option A stays operational. Block identity is unchanged. Network snapshot installation and pruning stay disabled. This document supersedes the S1, S4 and
S5 sections of `phase5-decisions-s1-s5.md` and the earlier `phase5-snapshot-recovery-design.md` wherever they differ; their corrections (voting-power thresholds, actual certificate encodings) stand.
Certificate validity rules (`check_header`, `verify_qc`, `verify_tc`) are NOT changed anywhere in this design.

**Revision 2 (audit of #140).** Resolves: peer-reported `TOO_LARGE` is advice only (3.3); the serving token bucket can admit a maximum response (3.5); install flushes the whole staged tree before any record or pointer is written, and checksums are corruption detectors only (4); every checkpoint root is retained, with defined fallbacks (2.3a); optional references do not guarantee checkpoint progress and lag can stall quorum formation (2.7); conflicting roots raise a generic alarm without attribution (2.5). `K = 1,000`, `ref_margin = 100` and every other number marked PROVISIONAL are devnet configuration, not safety guarantees: no safety property in this document depends on their values.

## 0. Defects resolved
| Concern | Resolution |
|---|---|

## 1. Operational baseline (Option A) and gating
Today: no snapshot is trusted. A node that falls behind uses validated block sync, or Step 1 header verification plus payload fetch (`check_payload`), and replays through the execution handoff. All finalized
payloads are retained. This design adds nothing to that. Gates, all default off and absent from the node binary until each acceptance group in section 7 passes on Linux and Windows:
`snapshot_install_enabled = false`, `pruning_enabled = false`, message kinds 7 to 14 are not decoded (`netmsg::decode` rejects them as unknown kinds), no `checkpoint_ref` in `BlockIdInput`.

## 2. Checkpoint references (S1; target architecture C, not implemented)
### 2.1 Encoding
`CheckpointRef = height u64 || block_id [32] || state_root [32]` = 72 bytes, big-endian. `ref_hash = SHA3-256("CFH1|ckpt|" || CheckpointRef)`. `state_root` is the application's canonical commitment to its state after
executing the block at `height`, and it equals `ExecCursor.state_digest` at that height (interim app: the hash chain value; the real application's canonical root is unverified and belongs to U5).
Genesis parameter `checkpoint_interval K >= 1`; devnet proposal `K = 1,000` (PROVISIONAL configuration, not a safety guarantee).

### 2.2 Where it lives (IDENTITY CHANGE, requires owner approval and a new profile id; not implemented)
A new optional block field `checkpoint_ref` (flag byte + 72 bytes, 73 bytes per block when present) enters `BlockIdInput` as `ref_hash` (absent = a fixed zero marker). Chains on profile v2 are unchanged and keep
today's ids. The header form (Step 1) gains the same field, so headers prove it.

### 2.3 Rules for a block that carries a reference (checked by every validator before voting)
* **R1 shape:** `height >= 1`, `height % K == 0`.
* **R2 finality:** `height <= F(B)`, where `F(B)` is the highest height final in the chain ending at `B.parent` once `B.qc` is counted: if `B.qc` certifies `C` and `C`'s parent `P` satisfies `commits_parent(P.round, C.round)` and is not genesis, `F = P.height`, otherwise `F` is what `C`'s own chain had. Deterministic from the proposal and the validator's chain; independent of local execution progress.
* **R3 identity:** the block at `height` on `B`'s own chain has id `block_id`.
* **R4 monotonic:** if an ancestor carries a reference, `height >=` the height of the most recent such ancestor reference, and at equal height the reference is identical (a REPEATED reference is therefore legal, however old).
* **R6 freshness of a new reference (identity-level rule, PROVISIONAL bound):** a reference whose height differs from the chain's most recent reference must satisfy `F(B) - height <= ref_max_age` (provisional devnet `10 x K`). A repeated reference (R4 equal height) is exempt.
* **R5 execution root** (the only rule that depends on local state), four outcomes. `Match`: the validator's root at `height` (see 2.3a) equals `state_root`: proceed to vote. `NotYet`: its executor has not reached `height`: do not vote now and re-evaluate when it does; deferral, not evidence; the round timeout applies as usual (timeouts never depend on references). `Unknown`: no root is obtainable locally by any path in 2.3a: do not vote, record no mismatch. `Mismatch`: do not vote; keep `{block_id, ref, own root}` as evidence (2.5).
**Proposer policy (not a validity rule, PROVISIONAL):** reference the newest multiple of `K` that is `<= min(F(B), own executor height - ref_margin)` with `ref_margin = 100` on the devnet, omit the field when none qualifies, and omit it for one leader rotation after one of its own reference-bearing proposals failed to gather a QC. References are optional, which means consensus can continue without them; it does NOT mean validators cannot stall on them: a reference-bearing proposal needs the votes of a quorum, and a validator that is lagging (`NotYet`), cannot check (`Unknown`) or disagrees (`Mismatch`) does not vote (2.7).

### 2.3a Root retention: how validators obtain every root they may be required to verify
Rule R4 allows a block to repeat an old reference, so a validator can be asked to check a root at any `K`-multiple, however far behind its executor is. The validator therefore keeps ALL of them:
1. **Root log (primary).** `checkpoint-roots`: an append-only file, header `"CFH1|roots|" || version u16`, then one 72-byte record per executed `K`-multiple: `height u64 || root [32] || tag [32]`, `tag = SHA3-256(previous tag || height || root)` (corruption detection only). It is never pruned and pruning must not delete it. Size: 72 bytes per checkpoint, about 15 MB per year at 6.7 blocks/s and `K = 1,000`.
   Ordering with the executor: when the executor will apply a block at a `K`-multiple it computes the new state digest, appends and syncs the log record FIRST, then publishes the new state. After a crash the log may be ahead of the executor cursor by exactly the next `K`-multiple; when that block is re-applied its digest must equal the logged root, otherwise raise the Execution-Consistency Alarm (2.5). A missing or damaged record below the cursor is rebuilt by the recompute path below, never guessed.
2. **Authenticated-ancestor equality.** If the validator holds no root for `height` (for example it installed a snapshot at `R` and `height < R.height`, so `root_floor = R.height`), but the reference is IDENTICAL to a reference carried by a block that is FINAL in its verified chain, the root is authenticated by that finality (2.4) and the outcome is `Match`.
3. **Recompute (bounded).** While pruning is disabled the validator still holds every payload since its `root_floor`; it may recompute the root by replaying from the oldest retained state, within `recompute_budget` (provisional 60 s of executor time); beyond that the outcome is `Unknown`.
4. **`Unknown`** is reachable only for a NEW reference older than the validator's `root_floor`; R6 bounds how old a new reference can be, and a repeated old reference is covered by path 2.
Pruning gate addition: pruning may not be enabled unless the root log is complete from the node's `root_floor` to its cursor.

### 2.4 How a joiner proves a checkpoint final
From a trusted start (genesis or a final anchor) the joiner runs `verify_header_chain` over the header chain until a header `X` that carries reference `R` is in `finalized` (needs `X`'s child and grandchild, or a final QC). It accepts `R` iff:
(a) `X` is final; (b) the verified chain has a block at `R.height` with id `R.block_id` (it is an ancestor of `X`, so final); (c) rules R1 to R4 hold along the verified chain. Why `R.state_root` is trustworthy: `X` is final, so a QC exists for `X`; its quorum voters each applied R5 and voted only on `Match`;
a quorum contains at least one honest validator when Byzantine power is below one third; that validator's own root equals `R.state_root`; execution is assumed deterministic. (A `Match` obtained by ancestor equality, 2.3a path 2, repeats a root already authenticated by an earlier final block, so the argument applies inductively.) Nothing is trusted from the snapshot server.

### 2.5 Divergence and alarms (no attribution without cryptographic evidence)
* **Mismatch against an uncertified proposal:** withhold the vote, keep the evidence, no halt. The proposer, a minority of validators, or the validator itself may be wrong, and one validator cannot tell which.
* **Certified contradiction:** the validator's own root at `R.height` differs from the reference in a block that is FINAL in its verified view (or carries a QC). A quorum accepted `R`, so under the stated fault model the validator is the outlier. It raises the **Safety/Execution-Consistency Alarm** (subtype `LocalDivergence`), stops signing, enters `Recovering` (section 5) and reinstalls through the section 4 path.
* **Conflicting certified references** (two blocks that are final or QC'd carry different roots for one height): raise the **Safety/Execution-Consistency Alarm** (subtype `ConflictingCertifiedRoots`) with the evidence (both references, block ids, the QCs) and stop signing. Conflicting roots do NOT by themselves establish cryptographic equivocation: they can come from nondeterministic execution, a software or version difference, or a bug. This document attributes nothing and prescribes no penalty. Equivocation is a separate finding that requires cryptographic evidence, for example two signatures by one key on conflicting votes for the same round, or two QCs for conflicting blocks whose signer sets overlap (each overlapping signer signed both); only that evidence may be used to name validators, and it is evaluated by a separate process.
* A local execution error, executor integrity-tag failure or crash-recovery inconsistency halts signing independently of any reference (subtype `LocalFailure`).
All alarms preserve evidence, never repair state automatically, and never touch the SafetyStore.

### 2.6 Snapshot authentication
A manifest request names the exact `CheckpointRef` the joiner authenticated (message 9). The installer recomputes the state root from the staged data and requires it to equal `R.state_root`, and the staged cursor to be `(R.height, R.block_id, R.state_root)`. A root or cursor taken from the snapshot, the manifest or the peer is never used for the comparison.

### 2.7 Limits of optional references, and the stall condition
* **Optional references do not guarantee checkpoint progress.** Leaders may omit the field indefinitely and consensus continues; no new authenticated checkpoint then appears, and joiners use Option A (header chain and payload replay). Leader slots are assigned round-robin over eligible validators BY COUNT (`leader_index`), not by power, so the fraction of omitting leaders can exceed the Byzantine power fraction; no lower bound on checkpoint frequency follows from the power assumptions alone. Monitoring: `checkpoint_age = F(tip) - last reference height`, alarm at `5 x K` (provisional).
* **Reference-bearing proposals can stall quorum formation.** Such a proposal gets a QC only if voters with power at least `Q = floor(2T/3) + 1` vote. Validators that are lagging, unable to check, disagreeing, offline or Byzantine do not. If their combined power exceeds `T - Q` (equal power: more than 333 of 1,000, more than 1 of 4), no quorum forms for that proposal; the round times out, a TC advances the round, and the next leader proposes. Severe execution lag therefore counts against the same fault budget as any other non-voting power. The leader-side omission after a failed reference-bearing proposal (2.3) bounds the stall to about one leader rotation per failure; it does not remove it.
* Provisional parameters (`K`, `ref_margin`, `ref_max_age`, the omission rotation, the alarm age) tune how often these situations occur. They are not safety guarantees.

## 3. Messages (S4): exact encodings, big-endian; new kinds 7 to 14 in the `CFH1|net|` envelope (12 bytes: tag 9, version u16, kind u8)
**Common rules.** Every request carries `request_id u64`. Every response echoes `request_id u64` then `status u8`, then the echoed selector fields. Status: `0 OK`, `1 NOT_FOUND`, `2 TOO_LARGE`, `3 BUSY`, `4 UNAVAILABLE` (not retained, or the feature is disabled), `5 AT_TIP` (header requests only). A non-OK response carries only the fields stated for it: `TOO_LARGE` the sizes in the table (advice only, 3.3); `BUSY` carries `retry_after_ms u32` (advice, clamped by the requester, 3.5); `NOT_FOUND`, `UNAVAILABLE` nothing further; `AT_TIP` `tip_height u64`. `OK` with a zero count is invalid and rejected.
The length of the whole message is checked against the kind's limit before parsing; each inner length and count is checked against the remaining input and its own maximum before anything is allocated; vectors grow by push, never `with_capacity(untrusted)`.

| Kind | Name | Body | Fixed size |
|---|---|---|---|
| 7 | HEADER_REQ | `request_id u64 \|\| after [32] \|\| max_headers u32` (1 to `max_headers_per_response`) | 12 + 44 = 56 |
| 8 | HEADER_RESP | `request_id u64 \|\| status u8 \|\| after [32]`; OK: `count u32 (>=1) \|\| count x (u32 len \|\| header) \|\| final_qc_flag u8 [\|\| u32 len \|\| qc] \|\| tip_height u64`; AT_TIP: `tip_height u64`; TOO_LARGE: `needed_bytes u64 \|\| next_height u64` | OK: 12 + 8 + 1 + 32 + 4 + count x (4 + header) + 1 [+ 4 + qc] + 8 |
| 9 | MANIFEST_REQ | `request_id u64 \|\| ref (72)` | 12 + 80 = 92 |
| 10 | MANIFEST_RESP | `request_id u64 \|\| status u8 \|\| ref (72)`; OK: `manifest`; TOO_LARGE: `needed_bytes u64` | OK: 12 + 8 + 1 + 72 + manifest |
| 11 | CHUNK_REQ | `request_id u64 \|\| snapshot_id [32] \|\| index u32` | 12 + 44 = 56 |
| 12 | CHUNK_RESP | `request_id u64 \|\| status u8 \|\| snapshot_id [32] \|\| index u32`; OK: `u32 len \|\| data` | OK: 12 + 8 + 1 + 32 + 4 + 4 + len |
`manifest = format_version u16 || snapshot_id [32] || total_bytes u64 || chunk_size u32 || chunk_count u32 || chunk_hashes [chunk_count][32]` (50 + 32 x chunk_count bytes).
`chunk_hash(i) = SHA3-256("CFH1|chunk|" || i u32 || data)`. **`snapshot_id = SHA3-256("CFH1|snapshot|" || genesis_hash || ref (72) || format_version || total_bytes || chunk_size || chunk_count || SHA3-256(chunk_hashes concatenated))`.** The id is content-addressed, so a snapshot is immutable by construction: the same id can only mean the same bytes. Two servers may chunk the same state differently and so produce different ids; that does not matter, because authentication is the state root of section 2.6, not the id.
Constraints (checked arithmetic): `chunk_count in 1..=65,536`; `chunk_size in 1..=1 MiB` and `61 + chunk_size <= transport limit` (the CHUNK_RESP overhead: `12 + 8 + 1 + 32 + 4 + 4`); `(chunk_count - 1) x chunk_size < total_bytes <= chunk_count x chunk_size`; `total_bytes <= max_snapshot_bytes` (devnet 256 MiB); every chunk but the last has exactly `chunk_size` bytes; the last has `total_bytes - (chunk_count - 1) x chunk_size`. Devnet `chunk_size = 256 KiB`.
Kinds 13 and 14 are reserved (`PAYLOAD_REQ` / `PAYLOAD_RESP` for fetching a payload by header hash) and not specified here.

### 3.1 Header responses: contents and worst case
Headers are returned oldest first, contiguous after `after` along the responder's final chain, and the response stops before the first header that would exceed the limit or `max_headers_per_response`. `final_qc` is a QC for the last header and is included only if it fits. `HDR_MAX(n) = 3,410 + QC_MAX(n) + 4 + TC_MAX(n)` is a TC-bearing header at the maximum certificate size (`QC_MAX(n) = 140 + ceil(n/8) + 3,315 n`; `TC_MAX(n) = 72 + ceil(n/8) + 3,323 n + QC_MAX(n)`). The smallest response a responder must be able to send, one TC-bearing header plus an additional QC, is
`HDR_RESP_MIN(n) = 12 + 8 + 1 + 32 + 4 + (4 + HDR_MAX) + 1 + (4 + QC_MAX) + 8 = HDR_MAX + QC_MAX + 74`.
Selection rule (exact): the fixed part of an OK response is `66` bytes (`12 + 8 + 1 + 32 + 4 + 1 + 8`); add headers, each costing `4 + len`, while `66 + sum <= limit` and the count is at most `max_headers_per_response` (devnet 64); then append the optional final QC (`4 + len`) only if it still fits. The result always contains at least one header or is a typed non-OK response.

### 3.2 Required transport limit (maximum permitted certificates, `k = n`, payload 64 KiB, 1,024 chunks of 256 KiB)
| n | `QC_MAX` | `TC_MAX` | `HDR_MAX` | `HDR_RESP_MIN` | proposal | binding requirement |
|---|---|---|---|---|---|---|
| 4 | 13,401 | 26,766 | 43,581 | 57,056 | 109,101 | 262,205 (chunk) |
| 31 | 102,909 | 205,998 | 312,321 | 415,304 | 377,841 | 415,304 |
| 100 | 331,653 | 664,038 | 999,105 | 1,330,832 | 1,064,625 | 1,330,832 |
| 1000 | 3,315,265 | 6,638,462 | 9,957,141 | 13,272,480 | 10,022,661 | 13,272,480 (12.66 MiB) |
Under the owner-locked 8 MiB limit the maximum permitted certificates support **at most 631 validators**; under 16 MiB (the libp2p receive cap, with zero margin and its framing overhead unverified) at most 1,264. A 1,000-validator network therefore needs a limit of about 13.3 MB, or a smaller maximum permitted certificate (a specification change this document does not make).

### 3.3 A valid object that exceeds the envelope: `TOO_LARGE` is unauthenticated peer advice
* **Configuration incompatibility is decided only locally.** At startup every validator derives the required limit for every enabled kind from its own parameters (`n`, payload limit, sync size, `chunk_size`; table 3.2) and refuses to enable the feature if its transport limit is lower. This is a local, static check with no peer involved. The only other source that could settle a size question is independently verified, signed object metadata; none exists today (object sizes are not committed by any signed identifier), so peer-reported sizes are never authenticated.
* **Responder:** when it holds a valid object that does not fit its own limit it answers `TOO_LARGE` with `needed_bytes` (and `next_height` for headers). It never truncates, splits or downgrades. This also covers the zero-fitting-header case: a count of zero is never sent as `OK`.
* **Requester treats `TOO_LARGE` purely as advice.** It never halts or changes recovery, never enters a terminal state, never counts toward the invalid-response suppression of 3.5, and never marks the peer invalid. Its only effects: a per-`(peer, selector)` cool-down (1 s, doubling to 5 min) and trying other peers. The reported `needed_bytes` is not used for any decision; it is logged and compared with the locally derived maximum for diagnostics only (a value above the local limit cannot describe a valid object under a configuration that passed startup, so it is simply not acted on).
* **Stall diagnosis, non-terminal:** if at least 3 distinct peers answered `TOO_LARGE` or did not serve the same selector for 10 minutes, the node raises a `RecoveryStalled` warning, printing its locally derived bounds so the operator can compare, and keeps retrying with backoff. Nothing is reset, halted or trusted instead.
* **An inbound frame larger than the limit** is closed by the transport before parsing and counted; it is not interpreted as `TOO_LARGE`.

### 3.4 Correlation
The requester keeps a table of at most `outstanding_cap` entries `(peer, kind, request_id, selector, deadline)`; `selector` is `after` (7), `ref` (9) or `(snapshot_id, index)` (11). A response is accepted only if it matches an entry on peer, kind, `request_id` AND the echoed selector, within its deadline; the entry is removed on acceptance. Anything else (unknown id, wrong peer or kind, selector mismatch, duplicate, late) is dropped and counted as unsolicited. `request_id` comes from a 64-bit counter started at a random value for each process and never reused within a process.

### 3.5 Bounds on allocation, concurrency and serving rate
* **Requester, per peer:** at most 1 outstanding HEADER_REQ, 1 MANIFEST_REQ, 4 CHUNK_REQ; globally `outstanding_cap = min(16, floor(max_recovery_memory / transport_limit))` (devnet `max_recovery_memory = 64 MiB`, so 8 at 8 MiB), and the feature refuses to enable if this is 0. Worst-case buffered bytes `<= outstanding_cap x transport_limit <= max_recovery_memory`. At most 3 peers in use. Deadlines: 30 s per request, 1 h per recovery. Chunks are written to the staging area, not held in memory.
* **Peer suppression is temporary and based only on locally verifiable invalidity:** 3 responses that fail local validation (bad hash, wrong echo, malformed, root mismatch) within 5 minutes suppress the peer for 10 minutes, doubling on each repeat up to 1 hour, and are forgotten after 1 hour without incident. Never permanent. `TOO_LARGE` and `BUSY` are never counted.
* **Responder concurrency:** at most 8 concurrent serves (served bytes in flight `<= 8 x limit`, 64 MiB at 8 MiB), at most 4 outstanding requests per peer, at least 100 ms between requests served per peer; excess requests get `BUSY`, never silence. `BUSY` carries `retry_after_ms u32`; the requester clamps it to 100 ms to 60 s (advice again).
* **Serving token bucket (fixes the burst contradiction).** Frames are atomic: the transport sends a whole message, so there is no partial or streaming debit. Admission is *reserve then refund*: when a request arrives the responder reserves its WORST-CASE response size from the peer's bucket (HEADER_REQ: the transport limit `L`; MANIFEST_REQ: `min(L, 143 + 32 x 65,536)`; CHUNK_REQ: `61 + chunk_size`), builds the response, and refunds the difference. If the bucket holds fewer tokens than the reservation, the answer is `BUSY` with `retry_after_ms = ceil((reservation - tokens) / refill)`. Invariants checked when the feature is enabled, otherwise it refuses to enable: **`burst >= 2 x L`** (so at least one maximum response is always admissible and a second is partly pre-funded), **`refill >= L / 4 s`** (a maximum response is admitted at least every 4 seconds from empty), and `aggregate_rate >= refill`. Devnet at `L = 8 MiB`: burst 16 MiB, refill 4 MiB/s (>= 2 MiB/s), aggregate 32 MiB/s. At `L = 13,272,480` (1,000 validators, maximum certificates): burst >= 26,544,960 and refill >= 3,318,120 bytes/s, so one header takes about 3.3 s of refill; header sync at that scale is slow by design, which is a consequence of the maximum permitted certificate, not of the bucket.

## 4. Atomic installation (disabled; protocol and recovery matrix)
**Integrity tags are not authentication.** Every durable record below ends with a SHA3-256 *integrity tag* over its bytes. The tag detects torn writes and accidental corruption ONLY. Anyone who can write the data directory can recompute it, exactly as they could rewrite the safety record or the application state; the trust boundary for local records is operating-system access control on the owner-only data directory, plus the cryptographic re-checks listed here. A record is never accepted on its tag alone where it contains authenticated objects.
Records, each replaced with write-temporary, `fsync` file, rename, `fsync` directory:
* `recovery.state` = `"CFH1|recovery|" || version u16 || phase u8 (0 Idle, 1 Staging, 2 Verified, 3 Published) || generation u64 || ref (72) || snapshot_id [32] || tag`.
* `install-record` (a LOCAL trust record: written only after this node's own verification succeeded; it is not a proof) = `"CFH1|install|" || version u16 || ref (72) || carrier (id, height, round) || tip final point (id, height, round, payload_hash) || high_qc (u32 len || qc) || tag`; at most `QC_MAX + 300` bytes.
* `app-current` pointer = `"CFH1|app-ptr|" || version u16 || generation u64 || state_dir (u8 len, at most 64 bytes) || cursor (height u64, block_id [32], state_root [32]) || tag`.
**Cryptographic re-checks at every start that finds an install record:** `high_qc` is verified with `verify_cert` against the validator set and genesis and must certify `tip.id` at `tip.round`; the pointer's cursor must equal `(ref.height, ref.block_id, ref.state_root)`; and after the engine is seeded, the first headers received from peers must link to `tip` (post-install continuity check), otherwise the Execution-Consistency Alarm. What these do NOT re-prove: that `tip` was final and that the carrier header was final; that rests on the earlier verification and on local access control.
**Durable ordering (each numbered step completes before the next begins):**
1. `recovery.state = Staging{ref, snapshot_id}`.
2. Stage each chunk under `staging/<snapshot_id>/`: write, `fsync` the file; `fsync` the staging directory after each batch; verify against `chunk_hash` on arrival.
3. When complete, build the SHADOW state tree under `staging/<snapshot_id>/state/`, recompute its root, and compare with the independently authenticated `R.state_root` and the staged cursor with `(R.height, R.block_id)`. Any mismatch discards the staging area, sets `Idle`, and publishes nothing.
4. **Flush barrier.** `fsync` EVERY regular file in the shadow tree, then `fsync` every directory bottom-up (`state/` and each subdirectory, `staging/<snapshot_id>/`, `staging/`). Nothing in steps 5 to 9 may start until the barrier has fully succeeded; any `fsync` error aborts the install (discard, `Idle`) and the node keeps its old state.
5. Rename `staging/<snapshot_id>/state` to `app/gen-<generation>` (atomic; the staging area and `app/` must be on the same filesystem, checked when the feature is enabled), then `fsync` `app/` and `staging/`.
6. Write `install-record` durably (temporary, `fsync`, rename, `fsync` directory).
7. `recovery.state = Verified`.
8. **Publish:** write `app-current` for `gen-<generation>` durably (temporary, `fsync`, rename, `fsync` directory). It is written only after the whole tree (step 4), the directory entry (step 5) and the install record (step 6) are durable; the single rename publishes application state and cursor together.
9. `recovery.state = Published`; seed the engine from `install-record` (section 5); `Idle`; delete the previous generation and the staging area.
| Crash point | Next start |
|---|---|
| steps 1 to 7 | pointer still names the old generation: old state and cursor intact; staging area and any orphan `app/gen-*` not named by a valid pointer deleted (only after the pointer verified; if it does not verify the node refuses to start and deletes nothing); `Idle` |
| during step 8 | the pointer is the old or the new one, never a mixture (atomic rename); both name complete, durable directories |
| after 8, before 9 completes | application is at `R`, engine behind: the install record is re-checked (above) and the engine is seeded; without a valid record the node refuses to start |
| after 9 | normal |
A damaged `recovery.state`, `install-record` or `app-current`, a pointer naming a missing directory, or a cursor that disagrees with the record: refuse to start and report; nothing is reset or guessed. The driver's `ExecutorAhead` refusal stays in force except for the one case where a valid `install-record` for exactly the executor's cursor exists. Execution after install replays heights `R.height + 1` to the committed tip once each through the normal handoff.
**Platform caveat:** directory `fsync` on Windows (opening the directory with `FILE_FLAG_BACKUP_SEMANTICS` and flushing) is the same primitive the safety store uses and is NOT verified to make a rename durable across power loss on NTFS; tests can show the ordering and crash outcomes with the `MemStorage` model, not NTFS power-loss behavior. The Windows confirmation of any implementation covers only what the tests can observe.
**SafetyStore is never read, written, reset or advanced by any step.** Its floors (`hvr`, `hqr`, last vote, last timeout) are byte-identical before and after every outcome in this table.

## 5. Recovery rounds and signing floors (QC/TC semantics, from `rules.rs`)
Floors: `hvr` = highest round voted or timed out in; `hqr` = highest QC round voted on (the lock). Rules that bind a recovering node: a vote at round `r` needs `r > hvr`, and `r == qc.round + 1` or a TC for `r - 1` with `qc.round >= tc.max_high_qc_round`; a timeout at round `r` needs reported `high_qc.round >= hqr`, `r > high_qc.round`, `r >= hvr` (a vote and a timeout in the same round are allowed), and `r == high_qc.round + 1` or a held TC for `r - 1`. Round advance: a QC or TC for round `c` moves the node to `max(current, c + 1)`; wall-clock time never moves a round.
A node in `Recovering` signs nothing (no vote, timeout or proposal) and proposes nothing, but serves what it holds. It becomes `Active` only when ALL hold: (1) the executor cursor equals the committed tip proven by the verified header chain; (2) the engine is seeded from `install-record` plus the QCs obtained since, and `engine.high_qc.round >= hqr` (a node whose lock is above the QCs it has must first obtain a QC of at least that round from peers; without it every timeout it could sign would be refused); (3) `round = max(max(high_qc.round, high_tc.round) + 1, hvr)`, computed, never chosen; (4) the first signature it makes obeys the unchanged rules above. The install changes none of the floors and signs nothing to "catch them up".
If no peer can supply (2) or the history, the node stays `Recovering` and reports it.

## 6. Certificates
Validity is unchanged. Transport limits assume the maximum permitted certificate (`k = n`), section 3.2. Power-aware selection is proposed separately in `phase5-certificate-selection.md` and changes nothing in this document.

## 7. Acceptance tests (each must also fail under a mutation that removes the rule it covers; mutation check required, as for Steps 0 to 1)
**E encodings.** E1 every kind round-trips and re-encodes byte-identically for each status (including `BUSY` with `retry_after_ms`). E2 every truncation and a trailing byte are rejected. E3 `OK` with count 0, unknown status, a chunk length not equal to the manifest rule, `chunk_count 0 / > 65,536`, `chunk_size 0 / > 1 MiB`, `total_bytes` outside the chunk bounds are rejected. E4 huge counts and lengths in tiny inputs are rejected without allocating (counting allocator). E5 sizes equal the formulas for the largest message of each kind at n = 4 and, with synthetic structures, at n = 31, 100, 1000, including a TC-bearing header plus an extra QC.
**C correlation.** C1 wrong `request_id`, C2 wrong peer, C3 wrong selector (`after`, `ref`, `snapshot_id`, `index`), C4 duplicate, C5 late, C6 table bounded, C7 ids never reused: all dropped and counted, none changes state.
**B bounds and serving rate.** B1 per-peer and global outstanding caps. B2 `BUSY` (with `retry_after_ms`) when over capacity, never silence. B3 a maximum-size response (13,272,480 bytes at n = 1000) is admitted from a full bucket with `burst = 2 x L` and the reservation is refunded to the actual size; from an empty bucket the `retry_after_ms` is within 1 ms of the computed value. B4 the feature refuses to enable when `burst < 2 x L`, `refill < L / 4 s`, `outstanding_cap = 0`, or the staging and `app/` directories are on different filesystems. B5 peer suppression: 3 locally invalid responses in 5 minutes suppress for 10 minutes, doubling to 1 hour, expiring after 1 hour quiet; `TOO_LARGE` and `BUSY` never count; no peer is ever permanently marked.
**O oversize (peer advice).** O1 a responder whose limit is below the next header sends `TOO_LARGE` with `needed_bytes` equal to the real minimal response size, and never `OK` with count 0. O2 a requester receiving `TOO_LARGE` with ANY `needed_bytes` (including `u64::MAX` and values below its own limit) does not halt, does not change recovery state, does not mark the peer invalid, and tries another peer; cool-down is per `(peer, selector)` only. O3 three peers all answering `TOO_LARGE` for 10 minutes produce the non-terminal `RecoveryStalled` warning and recovery keeps retrying. O4 startup refuses n = 1000 at 8 MiB and accepts it at a limit of at least 13,272,480, using locally derived bounds only (the decision is identical whatever any peer says). O5 an oversize inbound frame is closed before parsing.
**K references (vectors for the future identity change).** K1 profile v2 ids unchanged; v3 id changes with the reference. K2 each of R1, R2, R3, R4 and R6 rejects alone (R4 accepts a repeated old reference). K3 R5 `Match` / `NotYet` / `Unknown` / `Mismatch`. K4 mismatch against an uncertified proposal withholds the vote and does not halt. K5 mismatch against a final or QC'd reference raises the Execution-Consistency Alarm (`LocalDivergence`), halts signing and enters `Recovering`. K6 two final or QC'd blocks with conflicting roots raise `ConflictingCertifiedRoots` and attribute nothing; a separate test shows attribution requires the cryptographic evidence of 2.5 (overlapping-signer QCs) and is not produced from roots alone.
**S roots and storage.** S1 the root log records every `K`-multiple, survives restart, and its record is appended before the executor publishes (crash matrix on `MemStorage`: log ahead by at most one entry, reconciled when the block is re-applied; a mismatch raises the alarm). S2 a repeated reference far older than the validator's four most recent checkpoints still gets `Match` from the log. S3 after a snapshot install at `R`, a repeated reference below `R.height` identical to a final ancestor's reference is `Match` by ancestor equality; a new reference below `root_floor` is `Unknown` and the validator does not vote. S4 recompute path matches the logged root and stops at `recompute_budget`. S5 a damaged log record is rebuilt by recompute, never guessed. S6 the pruning gate refuses while the root log is incomplete.
**P authentication.** P1 a joiner accepts `R` only when the carrying header is final; P2 rejects a reference whose block is not on the verified chain or has another height; P3 altering `state_root` in a header breaks its id and signature; P4 a manifest for another ref or snapshot id is rejected before any chunk is fetched; P5 a snapshot whose recomputed root differs from `R.state_root` is rejected with nothing published.
**I install.** I1 staged data is validated against the authenticated root before any record or pointer is written. I2 the flush barrier: with fault injection, a failing `fsync` of any file or directory in the shadow tree aborts the install before step 5, and no `install-record` or pointer exists; a mutation that moves the pointer write before the barrier is caught. I3 the crash matrix of section 4 at every durable operation using the `MemStorage` crash outcomes: always the old state, or the new state plus a seedable record, never a mixture, and orphan generations are removed only after the pointer verifies. I4 damaged or missing `recovery.state`, `install-record`, `app-current` or directory: refuse to start and delete nothing. I5 a record that passes its integrity tag but carries a QC that fails `verify_cert`, or whose QC does not certify the tip, is refused; a record whose pointer cursor disagrees with its reference is refused. I6 `ExecutorAhead` exception only with a valid matching record. I7 SafetyStore files byte-identical after every scenario including crashes. I8 after install the executor runs `R.height + 1` to the tip exactly once each; headers that do not link to the installed tip raise the alarm.
**R rounds.** R1 zero signatures while `Recovering` (counting signer); R2 a node with `hqr = 50` and best QC round 40 cannot time out and stays `Recovering` until it obtains a QC of round >= 50; R3 the first vote has `r > hvr`; R4 the derived round equals `max(max(hqc, htc) + 1, hvr)`; R5 a vote and a timeout in the same round are both permitted, a lower round is refused; R6 a gap needs the previous round's TC and `qc.round >= tc.max_high_qc_round`.
**L liveness of references, under explicit execution-lag assumptions.** Let `lag` be the number of blocks a validator's executor is behind `F`. L1 (assumption: every validator's `lag < ref_margin`, all leaders honest) a new reference appears within one leader rotation (`n` rounds) after each `K`-multiple becomes eligible, and every validator votes on it. L2 (assumption: `m < n` leaders omit forever, by count) a reference still appears, within `n` rounds of eligibility. L3 (assumption: all leaders omit) the chain keeps committing, no new reference appears, `checkpoint_age` raises its alarm at `5 x K`, and a joiner completes by Option A. L4 (assumption: validators holding power greater than `T - Q` have `lag >= ref_margin`) reference-bearing proposals gather no QC, rounds time out, no validator signs a vote while in `NotYet`, and after the omission rotation the chain proceeds without references; the test asserts bounded recovery and no safety violation. L5 `NotYet` and `Unknown` produce no signature until `Match`. L6 with the stall condition exactly at the threshold (`power(non-voting) = T - Q` forms a QC; `T - Q + 1` does not).
**G gating.** G1 the config cannot enable pruning or snapshot installation; G2 kinds 7 to 14 are rejected as unknown by `netmsg::decode`; G3 no install code path is reachable in the node binary without the feature; G4 all existing suites pass unchanged on Linux and Windows.
